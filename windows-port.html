1. What you are building

A tray app for Windows 11 that turns the PC into a music display. When the PC has been idle for a few minutes, or on a hotkey, it opens a fullscreen Butterchurn (WebGL Milkdrop) visualizer that reacts to Spotify's audio and nothing else, with a now-playing overlay styled after the Spotify TV app. Any input closes it. It is not a real screensaver, just a fullscreen window on top of everything.

The goal is the same app, behaving the same way, looking like it belongs on Windows.

Spotify state Opens? Overlay
Not running, or no track No (a manual trigger flashes the tray icon) n/a

Song, paused Yes Progress bar only, frozen in place
Podcast Yes None

Playing on another device (Spotify Connect) Yes As above. The visuals get silence and drift slowly.

Not part of it

  • Other players, Spotify's Web API, any login.
  • A real .scr screensaver.
  • More than one display. The visualizer opens on the primary display only.
  • A welcome window (see section 4).
  • Distribution to other people: no code signing, no auto-update.
Owner decided, Windows
  • W1. You get this page plus the repository, and you run on the Windows PC.
  • W2. C# with WinUI 3 for the native UI and WebView2 for the page.
  • W3. Windows 11 only. No fallbacks for Windows 10.
  • W4. Tray icon: left-click opens a small flyout, right-click opens the usual Windows menu with Exit.
  • W5. Now-playing info comes from the Windows media controls. Song, podcast or ad is a best guess.
  • W6. No welcome window. The yellow icon and the error rows stay, for real problems.
  • W7. Personal use, unsigned, but with an installer (setup file, Start menu entry, uninstaller).

2. How you work

Where you run

You run on the owner's Windows PC, in a clone of this repository, in a native Windows shell (PowerShell, not WSL: a WSL session can't build or launch a WinUI app). That lets you build, start and test the Windows app yourself.

The owner's Mac has the finished app installed. It is the reference. You can't run it, so when something has to be compared by eye (the fade speed, the overlay position, how the visuals follow the music), ask the owner to look at both machines.

What the PC needs

  • Git and the GitHub CLI (gh), signed in.
  • The current .NET SDK (LTS) and the Windows App SDK workload for WinUI 3.
  • Node 22 or later, for npm run check (the page's tests).
  • The WebView2 runtime (part of Windows 11).
  • The Spotify desktop app, signed in.
  • An installer builder (see section 6, Install).

Check each of these first and install what is missing, asking before anything that needs admin rights.

How you check your own work

  • Unit tests for everything that needs no screen: a IdleViz.Core library with tests, ported from Sources/IdleVizCore and tests/IdleVizCoreTests.
  • A log file you can read while the app runs. The Mac app logs every open, close reason, preset change, Spotify change and audio status; do the same.
  • Debug switches, as on the Mac: keep the window open on input, open settings at launch, open the visualizer a few seconds after launch, fake a warning state.
  • The page's DevTools, in Debug builds only.
  • The owner, for anything that needs hands or eyes. If a test needs the PC to be idle, ask the owner to stop touching it rather than skipping the test.

Repository rules (from AGENTS.md)

  • main is protected. Every change is a branch and a pull request.
  • One build step is one PR, and it includes its tests.
  • PR titles are conventional commits with a scope. The body follows .github/PULL_REQUEST_TEMPLATE.md, with a Verification section that says what was not tested.
  • Update README.md at the end of every build step. Don't describe unbuilt things as working.
Owner decidedWorkflow. Pull requests with passing CI and no required approval. PRs written like those in pingdotgg/t3code. Squash merge. Claude may merge its own PR once CI is green. Tooling: Vitest, ESLint and Prettier for the page; XCTest and SwiftLint for Swift. Public repository, MIT license.
Claude's callJ1. Same repository, new windows/ folder. The Windows app lives in this repo and loads IdleViz/web/ as it is, so both apps share one page. Suggested layout: windows/IdleViz.sln, windows/IdleViz.Core/ (logic), windows/IdleViz.Core.Tests/, windows/IdleViz.App/ (WinUI), windows/installer/. CI gets a windows-latest job that builds and tests it. The test framework (xUnit is suggested) and the C# lint setup are not decided.

6. Behaviour, part by part

For each part: the rule, the numbers, and how to do it on Windows. The Mac file named in each heading is where the edge cases are written down and tested. Read it before you write the Windows one.

6.1 Triggers and open rules (Trigger.swift, OpenRules.swift, IdleScheduler.swift, IdleSkipRules.swift)

  • Four triggers: idle timeout, the global hotkey (default Ctrl+Alt+V), idleviz://open, and Open now in settings or the context menu. The last three are "manual".
  • Open rules, for every trigger: Spotify is running and has a current track, playing or paused. Songs, podcasts and ads all count. Use the state already known from the media-control events, so opening is instant.
  • Refused manual trigger: flash the tray icon. A refused idle trigger does nothing visible.
  • Idle: setting idleTimeout in minutes: 5, 10, 15, 30, or 0 for Off. Default 5. Don't poll on a fixed interval: schedule the next check for (timeout − current idle time), and re-check after wake and unlock.
  • One attempt per idle period. If the idle trigger fires and the open is blocked, don't try again until there has been new input.
  • Idle-only skip rules: the session is locked; the session isn't the one at the console (remote desktop, another user); another app is keeping the display busy.
  • After the keep-awake limit closed the visualizer, don't reopen until there has been new input, whichever trigger opened it.
  • A manual trigger while the visualizer is open does nothing, except in the debug no-dismiss mode, where it closes it.
Owner decidedDefault idle time 5 minutes. A blocked idle attempt waits for new input instead of retrying. The open check uses cached state and only asks Spotify when nothing is known yet. When Spotify plays on another device, it still opens (overlay as usual, silent visuals).
Check first"Another app is keeping the display awake." The Mac reads the system's list of display-sleep assertions, which covers a video or a call in any window. Windows only gives that list to an administrator. Without admin rights the nearest check is the shell's notification state (SHQueryUserNotificationState: a fullscreen app, a Direct3D fullscreen app, presentation mode). That misses a video or a call in a normal window. Ask the owner how to handle the gap: accept it, or also skip while any app other than Spotify is playing sound.

6.2 The window (WindowController.swift, Fade.swift, DisplayLayout.swift)

  • One borderless window covering the primary display, above everything including the taskbar.
  • Create it at launch, hidden, with the page loaded, and keep it between opens. Opening must be instant.
  • Remember the foreground window when opening, and give focus back to it on close.
  • Hide the cursor while open.
  • Fades: in over 0.6 s. Out over 0.25 s on input, 1.5 s at the keep-awake limit, none for sleep or a display change.
  • The PC is handed back when a fade-out starts, not when it ends: the cursor returns, focus goes back, the window stops taking clicks and the display request is released. The page and the audio keep running until the fade is over, so the picture doesn't freeze.
  • A trigger during a fade-out finishes the close and opens again.
  • Close without a fade when the PC goes to sleep and when the displays change: one added or removed, a resolution, scale or position change, another display becoming primary. Compare the full layout with the last one seen, and ignore change events where nothing differs.
Owner decidedFade everything, and make the input fade quick, like the system screensaver. Create the window at launch and keep settings open (this fixed the visualizer not showing over fullscreen apps on the Mac). A notification must never close it: on the Mac the cause was the Dock resizing, which looked like a display change.
Check firstFading a window that holds WebView2. The Mac fades the window's own opacity, so the desktop shows through. A WinUI window has no opacity setting, and a layered window may not work with WebView2's composition. Try window-level opacity first. If it can't be done, the fallback is to show the black window at once and fade the page in from black. That looks different from the Mac, so ask the owner before settling on it.

6.3 Dismiss, and the keys that don't (DismissTracker.swift, VisualizerKeys.swift)

  • Anything closes it: a mouse move with a real delta, a click, a scroll, any key or modifier, a touch or touchpad gesture. As sensitive as a screensaver.
  • Grace period 0.4 s after opening, so the trigger itself doesn't close it. Keys still held when it ends are "stuck": their release and their key repeat are ignored. Pressing one again closes the window.
  • Media keys keep it open and still do their job: volume up, down, mute, play/pause, next, previous, and brightness or keyboard-backlight keys where Windows reports them. Every other key closes it, F1 to F12 and the Windows key included.
  • Like key (L by default): toggles the preset on screen on the favorites. Ask the page which preset is showing at that moment (idlevizStatus()), then call showLike(true|false). The page shows a heart for 1.6 s: filled when added, outline when taken off, beside the title in the full layout, top right otherwise.
  • Skip key (N by default): calls skipPreset(). In Shuffle the page blends to the next preset in 0.5 s, whatever the blend setting is, and restarts the seconds-per-preset count. In Single it does nothing.
  • Key repeat doesn't run like or skip again. A modifier still closes the window, so Ctrl+L closes it.
  • Settings likeKey and skipKey hold a key code, or −1 for Off. Read them each time the window opens.
  • Backup check: every 100 ms compare the system's last-input time with the time since opening. If there was input the hooks didn't explain, wait 30 ms, check once more, then close.
  • Debug switch: turn dismiss off so the open page can be inspected.
Owner decided
  • Keys still held when the 0.4 s ends are ignored until pressed again (found by hand: holding the hotkey's modifiers used to close it).
  • Like and skip are plain keys picked from a list, not recorded shortcuts. Defaults L and N. The list has letters, digits, arrows and Space.
  • Like toggles and shows a brief heart next to the track title. Skip uses a quick 0.5 s blend and does nothing in Single mode.
  • Both rows sit in General, under Open hotkey.
  • Only the keys with a printed media function keep it open. Keys that open system UI keep closing it.
Claude's callJ3. Low-level hooks for input. Suggested: a low-level keyboard hook and mouse hook installed only while the visualizer is open. They need no permission and see input whether or not the window has focus. Two effects differ from the Mac, where like and skip only work if the app got focus: on Windows they would always work, and the key that closes the visualizer can be swallowed so it never types into the app behind. Key codes would be Windows virtual-key codes, which follow the keyboard layout, so the Mac's "labels are for a US layout" caveat goes away.

6.4 Keep awake and battery (Timing.swift, KeepAwake.swift, PowerSource.swift)

  • While the window is open, the display doesn't sleep and the screensaver and auto-lock don't start.
  • Setting keepAwakeLimit in minutes: 30, 60, 120, 240. Default 60. Counted from when the window opened. At the limit: fade out over 1.5 s, release the request, and let Windows sleep and lock as usual.
  • A changed setting applies at once to an open window, still counted from when it opened.
  • useBatteryTimes (default off), idleTimeoutBattery, keepAwakeLimitBattery. While the switch is on and the PC runs on battery, those two replace the normal values. A battery value never set counts as a copy of the normal one.
  • On a power-source change, reschedule the idle check, and apply the new limit to an open window (close at once if it is already past). Use the change notification, not polling.
Owner decidedStay awake with a time limit, default 1 hour, adjustable in settings. It opens on battery too, with an optional second pair of times behind a switch that reveals the extra rows, and the whole option is hidden on a machine with no battery. Accepted tradeoff: during the limit the computer doesn't lock by itself.

6.5 Hosting the page (PageView.swift, AppScheme.swift, AppSchemeHandler.swift, PageStatus.swift)

  • Serve the page from the custom scheme, not from file://: idleviz-app://app/… is the IdleViz/web/ folder, and idleviz-app://presets/… is the presets folder, .json and .js files only. Reject .., encoded .., links out of the folder, other hosts.
  • Send the Content-Security-Policy as a response header, a different one for index.html, plugin-host.html and converter.html. The exact strings are in AppScheme.swift. Send Access-Control-Allow-Origin: * with every response, because the plugin frame has an opaque origin.
  • Only allow navigation inside the scheme.
  • The page must have no way to call the app. Switch off web messages, add no host objects, and deny every permission request (camera, microphone, everything). The app talks to the page only by running script, and learns about the page only by asking it.
  • Wait for the page's scripts. After navigation completes, ask every 50 ms whether the page's functions exist, and only then send the current state (settings, presets, now playing, brightness, delay).
  • Status check: once a second while open, call idlevizStatus(). It returns the preset on screen, frame counts and new load failures. Treat the reply as untrusted: check its shape, cap strings at 300 characters and the failure list at 200.
  • Stuck page: no reply for 3 s means the page is stuck (a plugin in an endless loop). Throw the web view away and make a new one, send it the state again, mark the preset that was on screen as failed, and make sure the stuck renderer process is gone.
  • Reload and re-send state if the renderer process crashes.
  • The page only renders while the window is showing. Check that a hidden window costs nothing.
  • DevTools on in Debug builds only.

6.6 What Spotify is playing (NowPlaying.swift, SpotifyTracker.swift, SpotifyInfo.swift)

  • Use the Windows media controls and only Spotify's session (the desktop app and the Store app identify themselves differently; handle both). Never another player's session.
  • Event-driven: update when the session's properties, playback state or timeline change. No per-second polling.
  • From it: title, artist, album, playing or paused, position, duration, and the thumbnail.
  • Pass the thumbnail to the page as a data: URL inside the payload, JPEG, PNG or WebP only (checked by the first bytes). Keep the 5 most recent in memory. No artwork means the page shows a grey square with a music note.
  • "No track" is: no Spotify session, playback stopped or closed, or an empty title. The page waits 1.5 s before hiding the overlay, because a switch to a new album can report "no track" for a moment.
  • If reading the session fails, keep the last known track instead of clearing it.
  • The page moves the progress bar by itself from position plus time, minus the audio delay. While the window is open, re-read the position every 5 s to correct drift and catch seeks.
  • Never launch Spotify, and never control playback, except pause and resume around the manual delay test.
Owner decided, WindowsWindows media controls, no Spotify login. Song, podcast or ad is guessed, since Windows doesn't say. The Mac rules to reproduce: podcast → no overlay; ad after a song → "Advertisement" plus progress; ad after a podcast → no overlay.
Check firstWhat Spotify actually reports on Windows. Log it in the first spike, for a song, a paused song, a podcast, a local file and Spotify Connect:
  • Position and duration. If Spotify doesn't report a timeline, the progress bar and times can't be drawn. That is a product question for the owner, not something to work around quietly.
  • Podcasts. On the Mac a podcast has an empty artist. Find out what marks one here.
  • Ads. The owner has Premium and never saw an ad on the Mac either, so the ad rules are untested on both systems.
  • A track ID. There is no Spotify URL here, so a track change has to be detected from title, artist and album.
Owner decidedIf the track disappears or Spotify quits while the visualizer is open, the visualizer stays and only the overlay goes. This was asked twice and answered the same way both times. A failed read keeps the last known track. Five covers are cached.

6.7 Spotify's audio (SpotifyAudioTap.swift, AudioPump.swift, AudioAnalyzer.swift, AutoGain.swift, AudioFrame.swift)

Owner decidedThe visuals only ever get Spotify's audio. Not the system mix, not another app, not the microphone. If Spotify isn't there, the frame is silence, never a fallback source. Audio reaches the page only through audioFrame, and a plugin only gets a plain object of numbers. The audio is turned into levels in native code, not in the page.
  • Capture with WASAPI process loopback, targeting Spotify's main process and including its child processes. Run it only while the window is open (plus during Detect delay). Rebuild it when Spotify starts or quits and when the default output device changes. Clear the sample buffer on teardown.
  • Test for the guarantee: pause Spotify, play something else (a browser video, a system sound), and confirm the visuals stay flat.
  • Analysis, 60 times a second, on the newest 1024 samples: mono mix → automatic gain → Hann window → 1024-point FFT → 64 log-spaced bands from about 40 Hz to 16 kHz.
  • Bands: −65 dB to −10 dB maps onto 0..1 (a full-scale sine is 0 dB). Each frame a band moves 70% of the way up to a higher value and 12% of the way down to a lower one, and snaps to exact zero in silence. The lowest bands are narrower than one FFT bin, so they read a value interpolated between the two nearest bins.
  • bass, mid, treble are the averages of bands 0–7, 8–29 and 30–63.
  • Automatic gain: follows the frame's RMS, rising in about 0.5 s and falling in about 5 s, and scales it to 0.2. Gain stays between 0.5× and 32×, starts at 1×, is held while the input is below −60 dBFS, and is remembered between opens.
  • Drop frames, don't queue them, if the page falls behind.

The frame: 7,448 bytes, little-endian, sent base64-encoded

u32sequence
f32sample rate
f32 × 4bass, mid, treble, rms
f32 × 64bands, 0..1
f32 × 1024waveform, −1..1
u8 × 1024mono
u8 × 1024left
u8 × 1024right

The three byte arrays are Butterchurn's input: time-domain samples where 128 is silence. Byte offsets: header 0–23, bands 24, waveform 280, bytes 4376. tests/audio-frame.test.js checks the layout.

Check firstDo this spike before anything else is built on it. Prove that process loopback hears Spotify and only Spotify, find out whether it captures before or after Spotify's own volume slider, measure the cost of sending a frame 60 times a second by script, and check that Butterchurn holds 60 fps. On the Mac this spike found four bugs that would otherwise have shown up much later.

6.8 Audio delay (AudioDelay.swift in both folders, BeepTest.swift)

  • Bluetooth speakers play the sound 150 to 300 ms late and network speakers up to about 2 s, so the visuals wait to match. Keep analysed frames in a small buffer and send each one delay after it was captured. The page and plugins don't know about it. Opening the window clears the buffer.
  • Per output device: setting audioDelayByDevice, keyed by the default output device's ID. 0 to 2.5 s in 10 ms steps. Switch values when the default device changes. The hint under the slider names the device.
  • A device with no saved value starts at the latency the system reports for it.
  • Detect delay: only while Spotify plays out loud. Record the built-in microphone and the captured Spotify signal for about 5 s, cross-correlate them, and save the result if the peak is clear. If not (too quiet, a noisy room, headphones), keep the old value and say so in the hint. Stop the microphone at once. The recording stays in memory and is never sent to the page.
  • The method is in DelayDetector: a softened phase transform (magnitude to the power 0.8, 300 Hz to 6 kHz), smoothed over 5 ms, lags from −0.1 to 2.5 s. A result counts only if its peak is 10 standard deviations above the lags more than 100 ms away and 1.5 times the best of them. A lag below zero is saved as 0. Port it with its tests.
  • Use the built-in microphone even if a headset is the default input: recording from a Bluetooth headset's own microphone switches it to call mode and changes the delay being measured.
  • If Windows blocks microphone access for desktop apps, say so in the hint with a link to the microphone privacy page. This is only a hint. It never turns the tray icon yellow.
  • Manual delay test: pause Spotify if it is playing. Play a 60 ms beep every second, each placed at an exact time on the audio clock. Light the panel for 120 ms starting delay after each beep, read from the same clock. Every fourth beep is an octave higher (1760 Hz instead of 880 Hz) and its flash is orange. Done stops the beeps, saves the delay and resumes Spotify if the app paused it. Detect and the manual test can't run together.
Owner decided
  • An audio delay setting, plus a detector that uses the microphone, and the microphone turns on only when a button is pressed.
  • A new device starts at the delay it reports, not at 0.
  • The detector uses the phase-transform method (the first, loudness-based version worked half the time), measured from the moment the audio is handed to the app.
  • The manual test: drag until they match; a dialog on the settings window; a beep every second with the fourth one marked; Spotify paused, then resumed.

6.9 Presets (PresetSettings.swift, CustomPresets.swift, PresetLibrary.swift, MilkConverter.swift)

  • Bundled: 395 presets from four packs, already in IdleViz/web/vendor/. Nothing to do.
  • Settings sent to the page: visualizerMode (shuffle or single), singlePreset, shuffleFrom, secondsPerPreset, blendSeconds, favoritePresets, blockedPresets. A preset ID is its source, a colon and its name: bundled:Geiss - Swirlie 5, custom:pack/tunnel.json.
  • Blocked presets are left out of shuffle. A preset picked in Single is shown even if blocked. An empty filter falls back to all unblocked presets. Shuffle shows every preset once before any repeat.
  • Custom folder: created on first launch, subfolders allowed. .json Butterchurn presets, .milk Milkdrop presets, .js plugins. At most 5,000 files. Hidden files and folders are skipped. Watched for changes with a 300 ms debounce, ignoring the app's own cache writes.
  • .milk conversion runs in a hidden second web view on converter.html, one file at a time, abandoned after 10 s. Results are cached in Presets\.cache\<sha256>.json, keyed by the converter version and the file's contents. Check a file looks like a Milkdrop preset before converting, and treat "parsing failed" in the result as a failure.
  • Import… opens a picker for files or folders and copies them in. A taken name gets a number. Nothing is ever replaced. Open shows the folder in File Explorer. Reload rescans. Reveal selects the failed file in File Explorer.
  • Failures (with the page's error message) are listed under Failed to load and tried again when the file changes. They are not added to the blocklist.
  • The plugin author guide is docs/custom-visualizer.md. It applies unchanged.
Owner decided
  • The visualizer is built in (Butterchurn), not a separate visualizer app.
  • Custom presets come from a folder, and custom .js plugins are allowed.
  • Bundled packs: Base, Extra, Extra2 and MD1.
  • Defaults: shuffle all, 30 s per preset, 2.7 s blend.
  • A choice between one fixed visualizer and shuffle; "shuffle from" reuses the Favorites list.
  • Broken presets go on a separate failed list, not on the blocklist.
